## Observed changes

There are 9781 differing bytes in 859 runs. The first 0x100 bytes, and the ROMINFO/SECCTRL metadata region 0x270..0x400, are unchanged.

A bounded aligned ARM64 scan over [0x100,0xb0000) found 501 differing instructions. 498 are ADD/ADR/ADRP address materialization. The supplementary address-reference check resolves 492 to identical NUL-terminated bytes; six instructions (three ADRP/ADD pairs) refer to the build-time change `20260702-224917` -> `20261020-231629`. This supplementary local dataflow check is recorded in `address_reference_checks.json`; it is not a proof of whole-program semantic equivalence.

The other three changed instructions are at 0x6a660, 0x6a664, 0x6a66c. They change a predicate from `word == 0x454e454e` to `word != 0x44495341`. The containing function at 0x6a578 reads 0x34 bytes from the final 4KiB of `expdb`, and tests the word at buffer+0x24. Nearby messages identify a DFD/crash-data path. This is not evidence of changed LK authentication. The isolated four-instruction predicate passed Unicorn execution for 1004 values per version.

All changed aligned 32-bit words observed in [0xd1800,0x103e00) differ by -16 (37 words). This is consistent with relocated data references following the 16-byte string pool shift; complete pointer meaning is not asserted. Changes near 0x103ebc..0x103fdc are not decoded here. No claim that all executable regions or all anti-rollback mechanisms are recovered follows from this bounded comparison.

## Certificate parser and hash selection

Focused H4 Ghidra exports are in `decompile_h4/`, generated by `PreloaderFocus.java` into a fresh project `preload_h4`. Relevant entries:

- 0xa6508: certificate2 parsing/verification coordinator.
- 0xa5950: OID-field extraction.
- 0xa6100: TBS selection and signature verification workflow.
- 0xa6b40: builds encoded OIDs from the text table and searches ASN.1 nodes.
- 0xa6d9c: advances the ASN.1 cursor, with bounded remaining length.

The OID text table begins at file offset 0xe3df8, 64 bytes per entry: id5 = 2.16.886.2454.2.1 (payload hash), id10 = 2.16.886.2454.2.4 (header hash), id12 = 2.16.886.2454.2.9 (crypto-mode metadata).

Raw assembly at 0xa6608..0xa6644 corroborates this sequence: extract key, compare key, verify signature; only after success copy the verified TBS pointer/length into the ASN.1 extraction bounds. 0xa6758 preserves a nonzero verification error. Merely observing a later extracted hash does not imply the parser accepted the certificate.

`python fresh_analysis/preloader/emulate_cert_parser.py` executes the real ARM64 a6508 parser, ASN.1 scanning, and a6100 TBS selection for all three main certificates under both supplied preloaders. `parser_emulation.json` records results. This experiment explicitly mocks key extraction/equality, RSA primitives, byte reversal within mocked crypto, hardware/logging helpers, guard initialization and crypto sizes. SHA256 is computed in Python and the mocked RSA validity is gated on the exact known signed TBS hash. It is **not** secure-boot or device-acceptance testing.

For the H3 patched donor, both preloaders select the signed DER TBS at certificate input+0x2b8, length 645. Once the mocked crypto reports a valid signature, the extracted payload hash is the signed `77af9712f9533da9e85c629bbe5a63a7a40da08526c579b853b1256ba3f9a841`, not the prefixed `dc606f8db302a5895482b4f46799d34591a7bb00a777151101ac83812d862d78`. This establishes parser selection under the stated mocks. It does not establish the loader will enforce that digest on this device, nor does it establish what the separate bl2_ext stage verifies.

## Auth-required control path

The loader path around 0x7edxx calls policy lookup 0x8c934 and auth-required accessor 0x8cc18. The accessor returns `(policy >> 1) & 1`; it obtains policy from 0x8cad8. That routine consults a hardware/security-state query (0xa4b04), a device-state query (0x8c9f4), and per-image table bytes at +0x28..+0x2b. An ADR-derived table candidate begins at 0xed110 with 0x38-byte rows. The four policy bytes for all 18 examined rows are unchanged between supplied H3/ENG and H4 (`policy_table_candidate.json`), but partition-name pointer mapping and device runtime state are not established here.

When auth-required is zero, the loader logs a certificate parsing failure and continues to a different content-check path (call target 0xa7b00); when one, it treats verification failure as fatal and uses the standard content authenticator at 0xa54c4. These are static control-flow observations. They do not identify the actual flag value on the user's device. No changed explicit auth-policy flag was found within the examined table/code boundary; do not describe H4 as having hardened authentication on this evidence.

## Outstanding boundaries

- Exact on-device policy state, efuses, device state, and whether the supplied ENG image is the currently executing image are not measured.
- Main LK may be verified by another stage such as bl2_ext; that is a separate investigation.
- No full boot-chain simulation, hardware test, rollback-counter test, or signature root-of-trust validation was performed here.
- The prefix construction is not demonstrated as a bypass of the enforcing preloader parser; experiments show it reads the signed digest after signature success.

## Separate BL2 parser experiment (follow-up)

At the parent investigation's request, `emulate_bl2_parser.py` executes the actual extracted H3/H4 `bl2_ext` ARM64 certificate parser with the three certificate records and masks 0x60, 0x1f4e2, and 0x1f400. Results are in `bl2_parser_emulation.json`. No crypto/authentication-result or OID-scan mocks are used. Only PAC instructions and logging are bypassed, memory/BSS is initialized to zero, and the isolated function is called directly. This is parser execution, not boot-chain execution.

Both parsers return zero for these inputs. However their selected hashes differ for the patched H3 donor:

| BL2 version / entry | Mask | Extracted payload digest |
|---|---|---|
| H3 / 0x6cf8c | 0x60 or 0x1f4e2 | dc606f8db302a5895482b4f46799d34591a7bb00a777151101ac83812d862d78 (prefix) |
| H4 / 0x6d6bc | 0x60 or 0x1f4e2 | 77af9712f9533da9e85c629bbe5a63a7a40da08526c579b853b1256ba3f9a841 (signed TBS) |
| Both | 0x1f400 | Hash fields not requested |

This confirms a changed **BL2** hash-selection behavior, consistent with the H4 parser calling its TBS-scoping helper before OID extraction. It does not change the finding that the examined preloader authentication logic has no corresponding observed instruction/policy delta. A metadata-only parser call passing is insufficient to show a patched image will pass a later hash check. The duplicate-prefix technique from H3 cannot be declared compatible with unmodified H4 BL2 hash extraction on these results.

`validate_candidate_parser.py` repeats six calls for the parent agent's captured H4 candidate certificate. Evidence `BL2-CANDIDATE-PARSER-001` is in `hybrid_candidate_parser_validation.json`. Captured candidate image SHA256: 079161101778d288d5c43b860504320a394df3a363c50cf1054d94e8b417362b. The H3 parser extracts the candidate patched payload hash 848759443d2c436306e77df20bdcf87856fec4cb8806386c670db7a239385373; H4 extracts original signed db3e02a56f7e114b33631376128ef997c931f1111af0cf0f97f2aeb75f13a8e4. All six parser calls return zero. A certificate record snapshot permits checking identity if the parent later changes other container members. This is hash-selection validation only; no inference of mixed-version hardware compatibility.

## Preloader to BL2 load linkage

Raw xrefs establish a concrete layer boundary: preloader function 0x6a7a4 selects the string `bl2_ext` at file 0xc8d6c via instructions 0x6a7f0/0x6a7f4, finds its member offset through 0x7f424, and calls the generic image loader 0x7eeec at 0x6a820. Its caller at 0x6b168 invokes this function, and nearby 0x6b194 references the message `load BL2 extension`. This supports treating BL2's main-LK parsing separately from the preloader's own certificate parser. It does not establish the runtime authentication policy value.
